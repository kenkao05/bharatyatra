1
What is Supabase?

Supabase is an open-source backend-as-a-service. Think of it as a ready-made backend that gives you a database, authentication, file storage, and a REST API — without writing any server code. We use it instead of building our own backend.

PostgreSQL Database
Core
/* A real SQL database hosted for you. Tables: states, districts, attractions, accommodations, hospitals, etc. You query it like any SQL database. */
Auth System
Security
/* Handles login / logout / sessions. Admin logs in with email + password. Supabase issues a JWT token that proves who the user is. */
Storage
Media
/* File storage for images and videos. Buckets: state-images, state-videos, attraction-images, district-images. Returns a public URL you put in img src. */
Auto REST API
API
/* Supabase auto-generates a REST API for every table. The JS client wraps this so you never write raw HTTP requests — just method calls. */

Setting Up the Client

Before you can do anything — read data, log in, upload files — you need to create a Supabase client. This is done once and shared across all pages. In BharatYatra this lives in admin-auth.js and is available as window.sb.

admin-auth.js — Client Initialisation
Run once on every page
/* ───────────────────────────────────────────────────── STEP 1: Load the Supabase JS library (from CDN). This gives you the global `supabase` object. Every admin page has this in the <head>: ───────────────────────────────────────────────────── */ // <script src="https://unpkg.com/@supabase/supabase-js@2"></script> /* ───────────────────────────────────────────────────── STEP 2: Your project credentials. URL — unique address of YOUR Supabase project. KEY — the "anon" (public) key. Safe to expose. It only allows what RLS policies permit. ───────────────────────────────────────────────────── */ const SUPA_URL = 'https://gtpnojbbamoaznlutxap.supabase.co'; const SUPA_KEY = 'eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...'; /* ───────────────────────────────────────────────────── STEP 3: Create the client. `createClient` connects to your Supabase project. We store it on `window.sb` so every page can use it without creating a new connection each time. ───────────────────────────────────────────────────── */ window.sb = supabase.createClient(SUPA_URL, SUPA_KEY); /* ───────────────────────────────────────────────────── After this line, `sb` is available everywhere. Usage: sb.from('table'), sb.auth.signIn(), etc. ───────────────────────────────────────────────────── */
What does createClient() actually do? Think of it like making a phone call. Before your browser can talk to Supabase, it needs to "dial in" — it needs to know which Supabase project to connect to (that's the URL) and prove it has permission to access it (that's the key). createClient() establishes that connection and returns a client object (sb) you can use to fetch data, log in, upload files, and more. Storing it as window.sb means it's available globally — every page and every function shares the same connection without having to "dial in" again.
Anon key vs Service key. The anon key (used above) is safe to put in frontend code — it only has the permissions you define via Row Level Security. Never put the service_role key in frontend code; it bypasses all security.

Building the Frontend Page — Displaying Data Publicly

The public-facing HTML pages (states list, attraction detail, hospital finder, etc.) all follow the same pattern: load the Supabase client, fetch rows from a table, and render them into the DOM. No login required — the anon key + public RLS policy handles access automatically.

states.html — Page Head Setup
Public Page

Read
/* Run on DOMContentLoaded — no auth guard needed (public page) */ document.addEventListener('DOMContentLoaded', async () => { // 1. Fetch all states, sorted alphabetically const { data: states, error } = await sb .from('states') .select('id, name, slug, description, image_url') .order('name'); if (error) { console.error(error); return; } // 2. Build HTML cards and inject into the grid document.getElementById('states-grid').innerHTML = states.map(s => ` <div class="state-card"> <img src="${s.image_url}" alt="${s.name}"> <h2>${s.name}</h2> <p>${s.description || ''}</p> <a href="state.html?slug=${s.slug}">Explore →</a> </div>`).join(''); });
state.html — Load One State by URL Slug
Detail Page
/* Read ?slug=gujarat from the URL, then fetch that one row */ const slug = new URLSearchParams(location.search).get('slug'); const { data: state, error } = await sb .from('states') .select('*') .eq('slug', slug) // WHERE slug = 'gujarat' .single(); // expect exactly 1 row // state.name, state.description, state.image_url now available document.getElementById('state-name').textContent = state.name;
The golden pattern for every public page: (1) Include admin-auth.js to set up window.sb. (2) On DOMContentLoaded, call sb.from() to fetch data. (3) Check error first, then map data into HTML strings. (4) Set innerHTML on your container element. No login, no guards — the anon key handles public reads automatically.

Reading Data from the Database

Every public page (and admin page) fetches data using sb.from(). This translates to a secure HTTP request to Supabase's auto-generated REST API. You write it like a query builder — no raw SQL needed.

Basic SELECT — fetch all states
Read
/* sb.from('table') → target the 'states' table .select('*') → get all columns (like SELECT * in SQL) .order('name') → sort results alphabetically Returns: { data: [...rows], error: null or Error } */ const { data, error } = await sb .from('states') // which table? .select('*') // which columns? * = all .order('name'); // sort by name A→Z // data = [{ id:1, name:'Gujarat', slug:'gujarat', ... }, ...]
Filtered SELECT — attractions for one state
Read
/* .eq('column', value) is like WHERE column = value in SQL. .order() with ascending:false = ORDER BY priority_score DESC. Only select specific columns instead of * to keep it lean. */ const { data, error } = await sb .from('attractions') .select('id, name, short_description, priority_score, image_url') .eq('state_id', 1) // WHERE state_id = 1 (Gujarat) .eq('is_must_visit', true) // AND is_must_visit = true .order('priority_score', { ascending: false }) // highest score first .limit(10); // max 10 results
Count only — dashboard stat cards
Optimised
/* When you only need the COUNT (not the actual rows), pass { count: 'exact', head: true } to select(). head:true = don't return row data, just the count. This is much faster — used in admin-dashboard.html stats. */ const { count, error } = await sb .from('attractions') .select('id', { count: 'exact', head: true }); // count = 164 (no row data transferred)
Common Filter Methods
MethodSQL EquivalentExample
.eq('col', val) WHERE col = val .eq('state_id', 1)
.neq('col', val) WHERE col != val .neq('type', 'budget')
.in('col', [...]) WHERE col IN (...) .in('attraction_id', [1,2,3])

Authentication — Login & Sessions

Supabase Auth handles the entire login flow. When an admin signs in, Supabase checks the credentials, creates a session, and stores a JWT token in the browser. Every subsequent request automatically includes that token to prove identity.

What is a JWT? JWT stands for JSON Web Token — think of it as a digital ID card that Supabase hands you after a successful login. It's a small encoded string that says "this person is authenticated, their user ID is X, and this ID card expires in 60 minutes." From that point on, every request your browser makes to Supabase automatically includes that JWT. Supabase reads it and decides: "this request comes from a logged-in admin — I'll allow the write operation." Without a valid JWT, Supabase only allows public reads. You never handle the JWT manually — the client stores it in localStorage and attaches it to every request automatically.
admin-login.html — Sign In
Auth
/* signInWithPassword is the main login function. It takes { email, password } and returns: - data.session → the active session object - error → null if login succeeded, or an error object */ const { data, error } = await sb.auth.signInWithPassword({ email: '[email protected]', password: '••••••••' }); if (error) { // Login failed — show error message to user showError('Invalid credentials.'); } else { // Login succeeded — redirect to dashboard // The JWT token is now automatically stored in localStorage window.location.replace('admin-dashboard.html'); }
admin-auth.js — Protect Every Admin Page
Guard
/* BYAuth.check() runs at the top of every admin page. It reads the stored JWT and verifies it's still valid. If no valid session exists → user is sent back to login. */ window.BYAuth.check = async function () { // getSession reads the JWT from localStorage // and returns the current session (or null) const { data: { session } } = await sb.auth.getSession(); if (!session) { // No session — kick back to login page window.location.replace('admin-login.html'); return null; } // Session is valid — return it so the page can // read the admin's email / user ID return session; }; /* Every admin page calls this on DOMContentLoaded: */ document.addEventListener('DOMContentLoaded', async () => { const session = await BYAuth.check(); // guard fires first if (!session) return; // stop if not logged in // Safe to load page content now loadData(); }); /* Logout — signs out and redirects to login */ async function handleLogout() { await sb.auth.signOut(); // clears the JWT from localStorage window.location.replace('admin-login.html'); }

Row Level Security (RLS)

RLS is how Supabase controls who can do what to each table — enforced on the database side, not just in your JS code. Even if someone finds the anon key, they cannot write data without a valid admin session.

RLS Policy Logic for BharatYatra
Security
/* These policies are set in the Supabase dashboard under: Database → Tables → [table] → Policies ┌──────────────────┬────────────────────────────────────┐ │ Operation │ Who can do it? │ ├──────────────────┼────────────────────────────────────┤ │ SELECT (read) │ Anyone — anon key allowed │ │ │ (public pages need to read data) │ ├──────────────────┼────────────────────────────────────┤ │ INSERT │ Only authenticated admins │ │ UPDATE │ Only authenticated admins │ │ DELETE │ Only authenticated admins │ └──────────────────┴────────────────────────────────────┘ In SQL the read policy looks like: CREATE POLICY "public_read" ON attractions FOR SELECT USING (true); ← anyone can read The write policy: CREATE POLICY "admin_write" ON attractions FOR ALL USING (auth.role() = 'authenticated'); ↑ only if logged in via Supabase Auth */
Why this matters: Public visitors on bharatyatra.in use the anon key and can only read data. Admins logged in via Supabase Auth get an authenticated JWT, which unlocks write operations. The database enforces this — your JS code is just the messenger.

Writing Data — Insert, Update, Delete

Write operations (INSERT / UPDATE / DELETE) only work when the user is authenticated. Row Level Security on the Supabase side rejects any write attempt that doesn't carry a valid admin JWT.

INSERT — add a new hospital
Write
/* .insert(payload) adds a new row. payload is a plain JS object — keys match column names. Returns { error } — check error for success/failure. */ const payload = { name: 'AIIMS New Delhi', state_id: 1, // FK → states.id type: 'AIIMS / Central Govt', city: 'New Delhi', contact_phone: '011-26588500', rating: 4.8, created_at: new Date().toISOString(), }; const { error } = await sb .from('hospitals') .insert(payload); if (!error) toast('Hospital added!');
UPDATE — edit an existing row
Write
/* .update(payload) changes only the fields you provide. .eq('id', id) targets exactly one row by primary key. Always chain a filter — without it you'd update ALL rows! */ const { error } = await sb .from('hospitals') .update({ rating: 4.9, contact_phone: '011-99999999' }) .eq('id', 12); // ← only update row where id = 12
DELETE — remove a row
Write
/* .delete() removes the matching row permanently. Always use .eq() to target a specific row. CASCADE DELETE in the schema means deleting an attraction also deletes all its accommodations automatically. */ const { error } = await sb .from('hospitals') .delete() .eq('id', 12); // ← only delete row where id = 12
